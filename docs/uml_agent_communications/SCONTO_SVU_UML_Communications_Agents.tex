\section{Objectif}

Ce document présente, sous forme de diagrammes UML d'activités et de séquence, les communications implémentées entre les agents du modèle générique SCONTO-SVU. Il s'adresse à un lecteur qui doit comprendre le fonctionnement du système sans lire le code AnyLogic.

Chaque message, chaque agent et chaque séquence provient d'une vérification directe dans le fichier modèle \code{model/\allowbreak{}SCONTO\_SVU\_GENERIC\_MASTER.alp} (fonction \code{tracerFluxHierarchique()}) ou d'une trace runtime du Run 01 (EXP-0, seed 1001). Le fichier exact est cité en annexe (\S\ref{app:sources}). Lorsqu'un élément n'a pas pu être confirmé par l'une de ces deux sources, il est signalé comme tel plutôt que présenté comme acquis. Le détail des sources, de la méthode de confrontation et de l'historique de nommage entre versions du modèle figure en annexe (\S\ref{app:sources}).

Ce document ne modifie aucun fichier \code{.alp}, aucun code Java, aucun scénario JSON, et ne touche ni à la logique du modèle ni aux travaux de consolidation E4/E5 menés sur d'autres branches.

\section{Légende des agents et AER}

\subsection{Agents}

\begin{center}
\begin{tabularx}{\textwidth}{lX}
\toprule
Identifiant & Rôle \\
\midrule
\code{AS} & Agent stratégique : pilotage global, PI/SCOR consolidé (instance unique, \code{AS-sP1}). \\
\code{AT} & Agent tactique : arbitrage par macro-processus SCOR (\code{AT-sP2} Source, \code{AT-sP3} Make, \code{AT-sP4} Deliver). \\
\code{CA} & Coordinateur : coordination par macro-processus et par stratégie (\code{CA-sS1}, \code{CA-sM1}, \code{CA-sD1}). \\
\code{AOp} & Pilote opérationnel d'un poste ou groupe de postes (ex. \code{AOp-sM1.1}). \\
\code{AOe} & Agent d'exécution d'une micro-activité précise (ex. \code{AOe-sD1.8}). \\
\code{SupplierActor} & Acteur fournisseur externe. \\
\code{CustomerActor} & Acteur client externe. \\
\bottomrule
\end{tabularx}
\end{center}

\code{AOp} et \code{AOe} ne correspondent pas à des classes Java distinctes : \code{OperationalAgent} est une classe unique dont l'identifiant encode le rôle et l'activité. Cette distinction reste utile à la lecture des diagrammes.

\subsection{Catégories AER}
\label{sec:aer}

\begin{itemize}
  \item \textbf{AMENDMENT} (\textcolor{colAmend}{bleu, trait plein}) : instruction, plan ou demande descendant dans l'organisation.
  \item \textbf{EXECUTION} (\textcolor{colExec}{vert-bleu, trait plein}) : réalisation ou événement opérationnel constaté.
  \item \textbf{REPORT} (\textcolor{colReport}{gris, trait pointillé}) : retour d'information vers les niveaux de pilotage.
\end{itemize}

Cette classification correspond au premier paramètre littéral de \code{tracerFluxHierarchique(phase, émetteur, destinataire, message, ...)}.

Dans les diagrammes d'activités, les flèches neutres (\textcolor{colFlow}{gris-bleu}) représentent l'enchaînement des activités. Les catégories AER sont portées par les messages des diagrammes de séquence.

\subsection{Flux physique}

Un flux distinct des messages ci-dessus, le flux \textbf{physique} (\textcolor{colPhys}{brun}), représente le déplacement réel de matière ou de produit (fournisseur vers l'entreprise, produit fini vers le client). Il est annoté dans les diagrammes de séquence plutôt que représenté comme un message.

\subsection{Convention de statut de validation}

\begin{center}
\begin{tabularx}{\textwidth}{lX}
\toprule
Symbole & Signification \\
\midrule
\stRUN & Le message est présent dans l'ABox du Run 01 (seed 1001). \\
\stANT & Le message est présent dans l'ABox d'un run de validation antérieur, distinct du Run 01, déjà audité dans l'annexe \emph{Catalogue des messages inter-agents et Flux global} du dépôt de documentation. \\
\stIMP & Le message est journalisé par le code (\code{tracerFluxHierarchique}) mais absent des deux ABox disponibles. \\
\stNT & Aucun run documenté n'a exercé ce chemin (stratégies MTO et ETO). \\
\bottomrule
\end{tabularx}
\end{center}

Le mot \og{} validé \fg{} n'est utilisé dans ce document que pour une observation runtime (\stRUN{} ou \stANT{}), jamais pour une simple lecture de code.

\section{Architecture globale}

\begin{figure}[H]
\centering
\resizebox{\textwidth}{!}{\input{figures/01-architecture-globale.tex}}
\caption{Architecture globale des communications multi-agents SCONTO-SVU.}
\label{fig:archi-globale}
\end{figure}

Cinq niveaux de pilotage structurent le modèle : stratégique, tactique, coordinateur, pilote opérationnel et agent d'exécution. Une instruction descend d'un niveau à l'autre (AMENDMENT) jusqu'à l'exécution, seul niveau à interagir directement avec le fournisseur et le client ; un rapport remonte symétriquement (REPORT). Le flux physique relie directement les acteurs externes à l'exécution, sans passer par les niveaux intermédiaires.

Le modèle réel instancie plusieurs coordinateurs et pilotes, un par macro-processus SCOR (Source, Make, Deliver) : la figure n'en représente qu'un exemplaire par niveau pour la lisibilité.

\statut{\stIMP{} pour l'architecture prise dans son ensemble (confirmée par lecture des fonctions de génération d'identifiants) ; \stRUN{} pour la chaîne complète observée sur le cas MTS (\S\ref{sec:mts}) et pour la chaîne Source/Make observée via le réapprovisionnement autonome (\S\ref{sec:reappro}).}

\begin{figure}[H]
\centering
\resizebox{\textwidth}{!}{\input{figures/02-activite-flux-global.tex}}
\caption{Vue synthétique du flux métier, de la réception d'une commande à la clôture et au reporting.}
\label{fig:act01}
\end{figure}

Une commande peut suivre trois chemins selon l'état du stock de produit fini et de la matière au moment de son traitement. Ce branchement n'est jamais un choix du client : il résulte d'une décision interne calculée à partir de l'état réel du système. Les sections suivantes détaillent chacun de ces chemins.

\statut{\stRUN{} pour le chemin stock suffisant (\S\ref{sec:mts}) ; \stRUN{} pour les branches Source et Make, exercées par le réapprovisionnement autonome plutôt que par une commande cliente (\S\ref{sec:stock-insuffisant} à \S\ref{sec:make}).}

\section{Cas stock insuffisant : décision Source ou Make}
\label{sec:stock-insuffisant}

\begin{figure}[H]
\centering
\resizebox{0.75\textwidth}{!}{\input{figures/05-activite-source-make-deliver.tex}}
\caption{Décision matière et branchement vers Source ou Make lorsque le stock de produit fini est insuffisant.}
\label{fig:act0405}
\end{figure}

Lorsque le stock de produit fini est insuffisant, le système vérifie la capacité et la matière disponibles. Si la matière suffit, Make est planifié directement ; sinon, le fournisseur est consulté avant que Make ne soit lancé. Les deux branches convergent vers Make puis vers Deliver. Un ordre \code{REAPPRO\_*} entre par ce même point de décision, sans étape de réception cliente préalable (\S\ref{sec:reception}).

MTO et ETO empruntent le même point d'entrée qu'une commande cliente à stock insuffisant : le code ne les distingue pas au-delà de leur classification SCOR (\S\ref{sec:mts-mto-eto}).

\statut{Dans le Run 01, cette décision a été prise pour l'ordre de réapprovisionnement \code{REAPPRO\_1} : la matière a été jugée insuffisante et la branche fournisseur a été empruntée (\stRUN). Aucune commande cliente MTO ou ETO n'a exercé ce point de décision dans un run documenté (\stNT).}

\section{Réapprovisionnement autonome}
\label{sec:reappro}

\begin{figure}[H]
\centering
\input{figures/06-activite-reappro-autonome.tex}
\caption{Réapprovisionnement autonome par un ordre interne \code{REAPPRO\_n}.}
\label{fig:act06}
\end{figure}

La reconstitution du stock de produit fini est pilotée par une politique de seuil autonome, indépendante des commandes clientes, mais empruntant les mêmes points d'entrée Source et Make (\S\ref{sec:stock-insuffisant} à \S\ref{sec:make}). Un ordre \code{REAPPRO\_*} n'est pas une commande cliente : il est explicitement exclu de tout comptage de commandes clientes, mais sa clôture contribue à la terminalité opérationnelle globale au même titre qu'une commande cliente ouverte.

C'est cet ordre, \code{REAPPRO\_1}, qui a exercé dans le Run 01 la chaîne Source et l'exécution Make observées aux sections \ref{sec:stock-insuffisant} à \ref{sec:make} : le seuil de stock a été atteint, la matière a été jugée insuffisante, le fournisseur a été consulté, la production a été lancée sur 50 unités, et l'ordre a été clos avec le statut \code{SERVIE}. Le modèle réutilise pour \code{REAPPRO\_1} une chaîne de confirmation normalement associée aux commandes clientes (\code{PromisedDeliveryDate}, \code{OrderConfirmationOrder}, \code{CustomerConfirmationTask}), jusqu'à l'émission de \code{OrderConfirmed} vers \code{CustomerActor}. Cette réutilisation doit être distinguée de la logique métier attendue pour un ordre interne : elle est signalée ici comme une particularité de l'implémentation actuelle, sans qu'on en déduise un comportement métier souhaité.

\statut{\stRUN.}

\section{Reporting hiérarchique}
\label{sec:reporting}

Le reporting suit la catégorie REPORT introduite en \S\ref{sec:aer} (paramètre \code{tracerFluxHierarchique}) : chaque niveau consolide l'information reçue du niveau inférieur avant de la transmettre au niveau supérieur. Pour le macro-processus Deliver, la chaîne observée est \code{OperationalReport} $\to$ \code{ProcessStatusReport} $\to$ \code{MacroProcessReport}, visible sur la figure \ref{fig:seq06} (\S\ref{sec:deliver}). Pour Source, seul \code{OperationalReport} a été observé dans le Run 01 ; sa remontée au niveau stratégique n'a pas été isolée séparément. Pour Make, aucun message de reporting n'a été observé (\S\ref{sec:make}).

\statut{\stRUN{} pour Deliver ; \stRUN{} pour \code{OperationalReport} de Source ; \stIMP{} pour le reporting de Make.}

% ============================================================
% 13. COUVERTURE MTS / MTO / ETO
% ============================================================
\section{Couverture des stratégies MTS, MTO et ETO}
\label{sec:mts-mto-eto}

Le modèle utilise un traitement largement partagé entre MTS, MTO et ETO ; les diagrammes de ce document ne dupliquent donc pas artificiellement ce flux pour chaque stratégie.

\textbf{MTS} est observé en runtime dans le Run 01 (\S\ref{sec:mts}) : deux commandes clientes, \code{CMD\_1} et \code{CMD\_2}, ont suivi ce chemin de bout en bout.

\textbf{Source} et \textbf{Make} sont eux aussi observés en runtime dans le Run 01, mais par un ordre de réapprovisionnement autonome (\code{REAPPRO\_1}) plutôt que par une commande cliente à stock insuffisant (\S\ref{sec:stock-insuffisant} à \S\ref{sec:make}). Aucune commande cliente MTO ou ETO n'a été exercée dans ce run.

\textbf{MTO} est implémenté : une commande MTO emprunterait le même point d'entrée que la branche stock insuffisant (\S\ref{sec:stock-insuffisant}), et le code ne présente aucune branche MTO propre au-delà de ce point commun avec ETO.

\textbf{ETO} est implémenté par le même traitement partagé que MTO. Aucune phase d'ingénierie ou de personnalisation propre à ETO n'est représentée dans le pipeline de traitement de commande : la distinction ETO existe au niveau de la classification SCOR (niveau 3, groupes tactiques \code{CA-sS3}/\code{CA-sM3}/\code{CA-sD3}) et d'une constante de délai, pas dans le flux de messages présenté ici.

\statut{\stRUN{} pour MTS, Source et Make (par la voie du réapprovisionnement autonome) ; \stNT{} pour MTO et ETO en tant que stratégies de commande cliente.}

\section{Conclusion}

Le modèle met en \oe{}uvre une architecture de communication multi-agents structurée : trois catégories AER, cinq niveaux de pilotage, et un vocabulaire de messages stable entre les fichiers modèles audités. Le Run 01 confirme le chemin MTS complet, ainsi que la chaîne Source et l'exécution Make observées via l'ordre de réapprovisionnement autonome \code{REAPPRO\_1}. Les chemins MTO et ETO restent implémentés mais non exercés par un run documenté à ce jour ; ce document ne les présente pas comme validés.
